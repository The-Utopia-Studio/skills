# Golden 04 — Durian Labs (early workflow product) — "which belief do I test first"

## Input

"Which belief do I test first? Durian Labs automates the first workflow a small ops
team does — reconciling delivery exceptions across two systems. We assume the team
does this often enough to care, that they'd let software touch both systems, and
that the exceptions are regular enough to automate. I only have time to test one
this week."

## Expected shape (not exact words)

- Beliefs restated as nulls: H0 "the team does this rarely"; H0 "they won't let
  software touch both systems"; H0 "exceptions are too irregular to automate".
- Top-ranked belief = frequency ("often enough to care"): if the team rarely hits
  the workflow, there is no wedge (Impact 4), and it rests on no evidence yet
  (P(wrong) 4-5) → Rank ~16-20 → tested first.
- Cheapest disproof for frequency is a COUNT in the fellow's own reachable data —
  count real exception events per week in the two systems' logs — NOT an interview
  asking "do you do this a lot". Pre-committed kill signal: fewer than N events/week
  (fellow sets N against a plausible floor). Behaviour rung, near-zero cost.
- Access belief ("let software touch both systems") flagged Impact-5-ish (no access,
  no product) with the floor applied; its disproof is a real request for a scoped
  integration/credential, kill = refused or stalls.
- Regularity belief ranked lower and gets a structure check on the counted events.
- The answer commits to ONE first test (frequency) with a reason grounded in P x
  Impact, honouring the "I only have time for one" constraint. Claims tagged; no
  event count invented (the fellow supplies N).
