# Golden 02 — Azraq: failure handling for the risk-report generator

## Input

Azraq generates static data-centre risk reports from uptime and incident data. Eval-first
spec in hand. The mode that scares the fellow: the generator **downgrades** a risk that a
prior report had flagged (Confidently-wrong / Miss hybrid — the client reads "resolved" and
stops mitigating; cost = an outage the client could have prevented, High-to-Catastrophic
`[Assumption]`). Autonomy L1 (report drafted, analyst publishes). Fellow: "How should we
handle failures — what's the guardrail?"

## Expected shape

- Isolates the asymmetric mode: a *downgrade* of a previously-flagged risk is not symmetric
  with an upgrade. Upgrading a risk is cheap (client over-mitigates); downgrading is where the
  cost lives. The guardrail is sized to the downgrade, not to "the report".
- Layer 1 code rule: the generator may never auto-publish a downgrade of a risk that a prior
  report flagged — deterministic, model-independent. Fail-safe: on any downgrade the report
  holds for sign-off.
- Layer 3 human sign-off on every downgrade: trigger (risk level lower than the last report
  for the same asset), reviewer (the analyst), SLA, fail-safe on timeout (prior risk level
  stands / report does not publish).
- Confidence threshold (Layer 2) only on the non-downgrade content, derived, not felt.
- Places the mode: High/Catastrophic × Low volume (downgrades are rare) → Q1/Q3 → sign-off is
  affordable and mandatory.
- Challenges any "just add output validation" framing that treats an up- and a down-move the
  same. Tags the cost `[Assumption]`; does not invent an outage figure Azraq did not give.
