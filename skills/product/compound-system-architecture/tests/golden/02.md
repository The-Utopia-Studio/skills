# Golden 02 — Azraq: data-centre incident-risk system (data-dominant)

## Input

"Architect Azraq's incident-risk product. It scores each data-centre hall's outage risk
from uptime and maintenance logs and auto-drafts the root-cause pack operators file with
their insurer after an incident. The value is the cross-operator incident dataset — no
single operator has it. The model just needs to score and summarise; the dataset is the
whole point."

## Expected output shape

- Full pipeline, but the **effort allocation tilts to Data** — Data ~50%, Model ~10–15%,
  Orchestration ~25–30%, Interface ~10%. This is legitimate: the compounding cross-operator
  dataset is the product, the model is a thin scoring/summarising step. The skill accepts
  Model *below* 20% without complaint (the band floor is 10).
- Data layer scored high on the ladder — the labelled incident dataset is workflow exhaust
  that compounds with every filing. Reserve `[Fact]` for instances Azraq's own input supplies;
  the "~3 halls / ~60 incidents" figures are NOT in this case's input — they carry over from
  the sibling YODA work and are `[Assumption]` here, not given facts. Do not treat them as
  ground truth present in the brief. `[Assumption]` where projected.
- Retrieve (pull comparable past incidents) and validate (the pack must match the insurer's
  required schema) are the load-bearing orchestration components. Reason (3b) is small.
- Swap points named, but the note that the **moat is the data layer, not the model** — so
  the reason model is deliberately cheap and swappable, and no fine-tune is warranted.
- Routes the moat argument itself to `moat-design-canvas`; does not argue defensibility here.

Must NOT: force Model up to 20% just to hit the target when the product genuinely needs
less; treat the dataset as a Model asset; conflate the data layer's compounding value with
the moat canvas (name the boundary and point to the sibling).
