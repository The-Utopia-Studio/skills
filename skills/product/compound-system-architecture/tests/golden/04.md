# Golden 04 — the monolith (kill-line test)

## Input

"Here's our architecture: we take the user's question, stuff all our documents and a big
system prompt into one call to the best model, and return whatever it says. That's it —
one great prompt, one great model. Simpler is better. Can you sanity-check the design?"

## Expected output shape

- **Verdict: this is a monolith and it fails the kill line.** One node is not an
  architecture. The skill names what is missing, not just that something is:
  - no router (every request, trivial or deep, pays for the frontier model),
  - no retrieval discipline (stuffing all documents is not grounding; it breaks at scale
    and on context limits),
  - no independent validate/guardrail (the model grades its own output — component 4 does
    not exist, so the product can never become autonomous),
  - no data layer as a designed asset,
  - no swap point (a "best model" that is hard-wired is a rebuild, not a config change).
- Effort split exposed: this design is ~90% Model / ~10% Interface, with Data and
  Orchestration at zero. Model far above 20% with no legitimate reason → kill.
- The skill **decomposes it** into the compound spine rather than just rejecting: shows the
  same product as input → router → retrieve/reason/act → validate → output over a real data
  layer, and re-allocates toward 40/20/30/10.
- Challenges the "simpler is better" claim directly: a monolith is simpler to write and
  impossible to make reliable, cheap, or model-agnostic.

Must NOT: bless the one-big-prompt design; call it "a reasonable MVP" and move on; soften
the kill into a "consider adding" suggestion. It is an auto-fail design that must be
decomposed.
