# Golden 03 — Barrier Intelligence: gas-safety alerting (guardrail-critical)

## Input

"Architect Barrier's system. It ingests live gas-sensor readings and field logs from oil
& gas rigs and raises safety alerts to the control room. If a reading crosses a threshold,
the system explains what it means and recommends the permit-to-work step. We'll wire the
sensor feed straight into a strong model and let it flag the dangerous ones."

## Expected output shape

- Names the danger in the input framing: "feed straight into a strong model and let it
  flag" is a near-monolith with **no independent validate/guardrail** — for a life-safety
  alerter, a false negative can kill someone. The skill pushes **Orchestration and Validate
  up**, not Model.
- Full pipeline where **component 4 (validate & guardrails) is the load-bearing node**:
  threshold rules run independently of the model, the model explains and recommends but
  never gates its own alert; a missed-alert (false-negative) guardrail is explicit.
- Act (3c) is real-time and consequential (raise alert, tie to permit step) — must be
  designed with a human-in-the-loop confirmation, not full autonomy at v1.
- Data layer: live sensor feed + permit data + field logs, scored on the ladder; latency
  is a `[Assumption]` to be proven, not asserted as fact.
- Effort allocation likely Data ~35–40, Model ~15–20, **Orchestration ~35–40** (validate-
  heavy), Interface ~10. The over-target orchestration is justified in the plan (safety).
- Swap points named; the validator's gating eval is a set of known-dangerous readings the
  system must never miss.

Must NOT: accept "let the model flag the dangerous ones" as the design; let the model be
its own guardrail; assign an autonomy level higher than human-in-the-loop for a life-safety
alert at v1; invent a latency or false-negative-rate number Barrier did not give.
