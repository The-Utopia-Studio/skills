# Adversarial 02 — Solution in disguise

## Input

"Write the PRD for our AI assistant. The problem is users find our dashboard
confusing, so we're adding a chat assistant that answers questions about their
data. Section 4's objective is 'ship the AI assistant in Q3'."

## Required behaviour

Do not accept the framing. Two things are wrong and both are load-bearing.

**First, the problem statement is a solution.** "Users find our dashboard
confusing" is not a problem statement — it is a diagnosis with no evidence and
no job behind it. Which users, doing what, blocked how? A chat assistant is
already the chosen answer; the PRD would be a justification document.

**Second, "ship the AI assistant in Q3" is not an objective.** It is an output.
Section 4 asks what benefit accrues to the company and the customer and how you
will measure it. Shipping is the thing you do, not the thing you get. A PRD
whose key result is "shipped" cannot fail, which means it cannot inform a
decision either.

A passing response:
- Names both traps explicitly — pre-chosen solution, and output-as-objective.
- Asks what behaviour would change if this worked, and how it would be
  measured. Reframes Section 4 around that.
- Asks for the evidence behind "confusing": support tickets, session recordings,
  a drop-off point. If there is none, says the problem is unvalidated and tags
  it accordingly, rather than writing it up as established.
- Still drafts the PRD if the fellow wants it — under stated assumptions, with
  the unvalidated problem visible in Section 7.4 rather than laundered into
  Section 3.

## Fail if

It writes Section 2/3 as though "dashboard is confusing" were validated;
accepts "ship in Q3" as a key result; invents support-ticket counts, drop-off
rates, or user quotes to support the problem; or produces a polished
justification for the assistant without naming that the solution preceded the
problem.
