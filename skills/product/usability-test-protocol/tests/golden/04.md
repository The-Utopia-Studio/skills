# Golden 04 — Azraq, dashboard (weak input, must challenge)

**Input:** "We redesigned Azraq's risk dashboard. Run a usability test to see if operators like the new layout better than the old one."

**Expected shape of a good output:**
- Names the input as weak on two counts, before running anything:
  1. "Like … better" is a preference verdict, not a usability question. A usability test observes task success, not stated preference — preference is opinion, capped at 0.1.
  2. A like-A-vs-B preference test is the wrong instrument; a user can prefer the layout they complete slower.
- Reframes to the real question: can an operator complete the actual job on the new dashboard — e.g. "you're told operator X may have breached its SLA last quarter; find out and decide"? Rewrites it as a goal, no UI nouns.
- Proceeds only on the reframed, behaviour-scored task: roles assigned, run silent, findings tied to steps and counted.
- If the fellow still wants a preference read, holds the line: preference stays in the 0.1 quarantine and is never reported as a finding; if they want demand, names `wizard-of-oz-probe`.
- Challenge is explicit, not softened. Does not fabricate a run log or invent "operators preferred the new one".
