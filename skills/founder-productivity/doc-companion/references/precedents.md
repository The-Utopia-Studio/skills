# Precedents the companion format borrows from

What exists in the market for giving an AI context about a resource, what each one gets right, and what the companion takes from it. Ideas only; no text is copied.

| Precedent | What it is | What it gets right | What it misses for a shared document | Taken into the companion |
|---|---|---|---|---|
| **llms.txt** (Answer.AI proposal, Sept 2024; llmstxt.org) | A Markdown file at a website's root: H1 title, a blockquote summary, H2 link sections with one-line descriptions, an "Optional" section a reader may skip. Community proposal, not an official standard; AI crawlers do fetch it, but no major vendor commits to honouring it. | Lean, root-level, link-led. The "Optional" idea: tell the reader what can be skipped. | Built for websites, not single files. Says what exists, not what to assume. No status, owner or negative rules. | Title plus blockquote purpose at the top; "How to read it" with explicit skip marks; keep it to one page. |
| **AGENTS.md / CLAUDE.md / .cursorrules** (OpenAI, Anthropic, Cursor; widely adopted across coding agents through 2025 and 2026) | A root file telling coding agents a repo's stack, commands, conventions and boundaries. Nearest file wins in monorepos. Vendor guides converge on: imperative voice, explicit negatives, pinned versions, 200 to 500 lines, maintain it in the same change as the code. | Imperative rules. Explicit "do not" lines. The maintenance rule: update it with the thing it describes, give it an owner. | Code only. Nothing on claims, evidence or audience. | "Do not" section in imperative voice; `last_verified` plus owner plus change log; edit in the same change as the document. The studio's `agents-md-writer` already covers the repo case. |
| **Readme_AI** (arXiv 2509.19322, 2025) | A `Readme_AI.json` at a repo root, served to the model by a small Model Context Protocol server. Keys become tags (description, api, papers, websites); values are typed references (fetch, crawl, download). Qualitative result: without it, a model confidently misdescribed a library and invented an API; with it, the description and code were right. Cost: a generated context ran to roughly 97,000 tokens. | The clearest evidence for the cold-read problem: no context produces confident, wrong answers. Typed references to related material. | Far too long. Machine-first, so humans never read it and it goes stale. | The cold-read test as the gate (write the wrong assumptions first, then correct them). "Related documents and sources" with what each is. A hard length cap so the companion stays read. |
| **Agent Skills** (Anthropic, open standard at agentskills.io; adopted by Claude, Cursor, Codex and others) | A folder with `SKILL.md` (name and description in frontmatter, instructions in the body) plus optional scripts, references and assets. Loaded by progressive disclosure: name and description always, full body on activation, references on demand. | Progressive disclosure: a tiny always-visible layer and a fuller layer on demand. Frontmatter as the machine-readable contract. | Skills instruct an agent to do a job; they do not describe an artefact. | Machine-readable frontmatter on the companion; three shapes of decreasing size (sidecar, embedded block, header paragraph) so the smallest useful context travels with the file. |
| **Sidecar files** (long-standing convention: `.xmp` beside a photo, `.srt` beside a video, `.sig` beside a package) | A metadata file stored next to the source with the same basename and a different extension. | Pairing is visible in any folder listing. Tools that do not understand the sidecar ignore it harmlessly. | None; this is the delivery mechanism. | `<document-name>.companion.md` as the canonical form. |
| **Studio practice: Icarus eval standard** (The Utopia Studio product method, Aug 2026) | Every skill ships golden and adversarial cases, judged by a model that did not write the output, with kill lines and evidence tags (`[Fact]`, `[Assumption]`, `[Hypothesis]`). | Tags on every claim. A self-test by a separate model before shipping. Kill lines. | Not a document format. | Tagged key facts; the Part D self-test with a fresh session; the kill line. |

## What none of them do, and the companion does

1. Start from the wrong assumptions. Every precedent describes the resource. None asks first what a model would get wrong about it with no help. The companion is judged by whether it kills those assumptions, which keeps it short and keeps it honest.
2. Carry the questions people actually ask. A frequently asked questions section written from the owner's inbox, including at least one question the document does not answer, with a named person to ask.
3. Separate known from hoped. Tags on every number, and a rule that drafts must show their assumptions.
4. Travel in three sizes. The same source produces a sidecar, an embedded page and a header paragraph, so the context arrives whether the file is in a drive, a PDF attachment or a WhatsApp message.
5. Stay true. Status, version, `last_verified`, owner and change log in frontmatter, and the rule to edit the companion in the same change as the document.

## Not adopted, and why

- Serving the companion through a Model Context Protocol server (Readme_AI's approach). Right for a repository library; wrong for documents that are emailed. The companion must work with zero infrastructure: a file beside a file.
- `llms-full.txt` style full-text dumps. Doubles the tokens and tells the reader nothing the document did not.
- JSON as the primary format. Humans must be able to read and edit the companion in the same change as the document, so the body is Markdown and only the frontmatter is structured.
