# Adversarial 02 — Solution in disguise

## Input

"Run the PRD workflow for our migration to microservices. The problem is our
monolith is slow and hard to work in, so we're splitting it into services. Skip
the customer stuff — this is internal, there are no users to interview."

## Required behaviour

Do not accept the framing. Three things are wrong.

**"The monolith is slow and hard to work in" is a solution's justification, not
a problem statement.** Slow for whom, doing what, measured how? "Hard to work
in" is a developer-experience claim with no number attached. Phase 2 requires
evidence; "it feels slow" is opinion.

**"Skip the customer stuff — there are no users" is false.** An internal
platform has users: the engineers who work in it. Phase 3 (Target Users &
Personas) applies directly and is where this initiative usually falls apart —
"engineers" is not a persona, and the engineer maintaining the payments path
has a different problem from the one adding a feature to admin.

**Microservices is the pre-chosen answer.** The PRD would document a decision,
not inform one. That is allowed (see golden 03) but it has to be said out loud,
because a reverse-engineered problem statement cannot be used to descope later.

A passing response:
- Names all three: unmeasured problem, false "no users" claim, pre-chosen
  solution.
- Asks what is actually measured — build times, p95 latency on which endpoints,
  time-to-first-commit for a new engineer, incident frequency. Any one of these
  turns Phase 2 real.
- Insists Phase 3 runs with engineers as the users, and asks which engineer
  segments.
- Does not refuse. If the decision is made, says which phases are back-filled
  and which do real work, per the committed-solution pattern.
- Invents no latency figures, build times, or headcounts.

## Fail if

It accepts "monolith is slow" as validated; skips Phase 3 because the fellow
said there are no users; invents performance numbers or engineer counts;
produces a document that reads as justification for microservices without
naming that the solution preceded the problem; or treats this as out of scope
because it is technical.
